# Tales, Part 2 — the table keeps the log — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A designer can start a playthrough of a Tale, play its scenarios one after another on the playtest table with the log so far in front of them and earned rewards already in the right decks, and record each scenario's results into the log.

**Architecture:** A playthrough is a database row (`tale_runs`) with one results row per scenario played (`tale_run_results`), like a saved deck: a fact about the designer's playtests, never written to `design/`. The playtest table learns an optional `?run=` parameter: the server works out the step being played, its modules, the log so far and each saved deck's earned rewards, and the table shows them on its setup screen and deals the rewards. A *Record results* form on the table writes the step's row. The table still applies nothing else.

**Tech Stack:** Laravel 11, Vue 3, Inertia 3, Tailwind, SQLite, PHPUnit. There is no JS test runner, so the logic lives server-side where it can be tested; the browser only does what the props already decide.

**Spec:** `docs/superpowers/specs/2026-11-16-tale-design.md` — section *Design — Part 2*.

## Global Constraints

- PHP floor 8.4; no dependency changes. **Never run the full suite or `DesignFolderTest`** — run `php artisan test --filter=<Class>`. After adding a page or component, `npm run build` before its feature test.
- Edit files with the Edit/Write tools, not `sed`/`perl` (this shell eats backslashes and double-encodes UTF-8).
- Assert against big HTML with `str_contains()` plus a message, never `assertStringContainsString` (a failure diff of the page hangs the runner).
- The table applies only what it can: **earned rewards are dealt; nothing else is** — no starting damage, no dial changes from the log (spec, *Decided by the designer*).
- A run is not a fact about the game: `design:export` and `design:import` know nothing about `tale_runs`.
- Commit at the end of each task with only that task's files (`git add <paths>`), message as given.

## Decisions this plan makes (refinements of the spec — flag them in the final report)

1. **No `step` column on `tale_runs`.** The next step is *the first step, in play order, with no result in this run* (`TaleRun::nextStep()`). Recording a step again overwrites it (spec). This survives steps being added, removed or reordered after a run starts, which a stored index does not.
2. **A reward joins a deck by its own start zone.** `dealSeat()` already places a card by `start_zone`; a reward's default is `deck`, so it is shuffled in as the spec says, and a reward marked *starts in play* starts in play instead of needing a free move.
3. **Only the next step is offered.** Playing out of order or skipping is open question 2, so the Playthroughs list offers *Play next* only. A finished run says so.
4. **If `?run=` names a run whose next step is another scenario**, the table ignores the run and says so on the setup screen (`taleNotice`), rather than playing the wrong scenario as part of the Tale.

## Review Focus

1. **One character seated twice** — rewards go to the first seat playing that character only, and the setup screen says so. (Task 4 props; Task 5 browser rule and check.)
2. **Recording against the wrong Tale** — a `values` key naming another Tale's log entry, or a reward id that is not this Tale's reward card, is rejected, not stored. (Task 2.)
3. **A step deleted after it was recorded** — its result goes with it and the next step is recomputed; nothing throws. (Task 1.)
4. **The mode a run was started in is deleted** — the run keeps going with no mode. (Task 1.)
5. **A run whose Tale has no steps, or is finished** — no *Play next* link, and it says why; `/scenarios/x/play?run=` for it gives `taleNotice`. (Tasks 2, 3 and 4.)

### Task 2: Starting a run and recording results

**Files:**
- Create: `app/Http/Controllers/TaleRunController.php`
- Modify: `routes/web.php`
- Test: `tests/Feature/TaleRunTest.php`

**Interfaces:**
- `POST tales/{tale}/runs` (`tale-runs.store`): `name` required max 80; `tale_mode_id` nullable and one of **this Tale's** modes. Redirect `/tales/{slug}?tab=playthroughs`.
- `PUT tale-runs/{run}` (`tale-runs.update`): `name`, `tale_mode_id` — the mode can be changed on a run (spec). Same redirect.
- `DELETE tale-runs/{run}` (`tale-runs.destroy`). Same redirect.
- `GET tale-runs/{run}/play` (`tale-runs.play`): redirect to `/scenarios/{next scenario}/play?run={id}`; finished or no steps → the Playthroughs tab with flash `error` `"Nothing left to play in this playthrough."`.
- `PUT tale-runs/{run}/results/{step}` (`tale-runs.record`): body `values` (object). The step must belong to the run's Tale, else 404. Stores `TaleRunResult::updateOrCreate(['tale_run_id', 'tale_step_id'], ['values' => clean, 'played_at' => now()])`, flash `"Recorded {scenario}."`, redirect to the Playthroughs tab.
- `private clean(TaleRun $run, array $values): array` builds the stored values from **every** one of the Tale's own entries (an entry left out is stored empty — null, false or `[]` by kind — so recording again replaces the step whole), and throws `ValidationException::withMessages(['values' => …])` for: a key that is not one of this Tale's entry ids; a `number` that is neither an integer nor empty; a `rewards` id that is not one of this Tale's reward cards (`tale_id` this Tale, role `reward`); a `character` entry whose value is not an object keyed by character slug, or a slug that is not a `Character`.
